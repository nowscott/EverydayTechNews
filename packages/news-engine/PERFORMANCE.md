# 第一批评分迁移验证 · 2026-10-18

以下是第一批评分迁移的历史测量：TS 的评分、明细、信号、兴趣、入选顺序及排除原因与 Python 一致。测量当时内部试刊仍运行 Python，测速没有调用模型或SMTP。后续完整TS内测上线状态见 [MIGRATION.md](MIGRATION.md)，不以此表推断整条链路提速。

## 环境与方法

Apple M4 / macOS ARM64，Node v24.14.1、Python 3.14.7。结果为本地测量，不能代表 GitHub Actions 或整封早报性能。原始计时和环境信息见 [benchmark-results.json](benchmark-results.json)，复现命令见 [README.md](README.md)。

- 合成408篇和10000篇，目标选32篇；真实样本为已有冻结期刊的20篇，正文哈希与90天期限已验证，未为实验重新采集或生成。
- 每组先核对 Python/TS 完整 JSON 输出，再测三种实现；每种三个新进程、每进程一次预热和五次计时，取15次中位数，相邻轮交替执行顺序。
- 热处理计时排除输入读取/复制及一次配置加载，包含评分、排序与输出对象构建。原 Python 保留逐篇读配置；Python配置复用版本仅在独立参考进程替换配置加载函数，不修改生产代码。
- 冷调用为另外五次完整进程调用的中位数，含导入、输入/配置读取、计算、JSON输出与进程退出；Python经过参考脚本，TS经过原生TS CLI。空进程启动另测，不能与热耗时相加。
- RSS 为每个进程预热、复制及重复执行后的峰值，再取三个进程中位数；包含运行时、输入、垃圾回收和测试工具的开销，不是排序函数的独立内存。Node structuredClone 与 Python deepcopy 对不可变字符串的处理不同，不能仅据此推断生产内存倍数。

## 热处理结果

| 输入 | 原 Python | Python 配置复用 | TS | 原 Python / TS |
|---|---:|---:|---:|---:|
| 合成408篇 | 15.475 ms | 6.558 ms | 6.974 ms | 2.22倍 |
| 合成10000篇 | 371.286 ms | 165.447 ms | 154.419 ms | 2.40倍 |
| 真实20篇 | 1.086 ms | 0.653 ms | 0.436 ms | 2.49倍 |

TS相对配置复用Python，408篇约慢6%，10000篇约快7%，真实20篇约快1.50倍；小样本绝对差只有约0.2毫秒，不宜据此预测长期吞吐。单独减少重复配置读取，就已取得大部分热处理收益。本轮没有得到十倍语言加速的证据。

## 启动与内存

空进程启动中位数：Python 19.308 ms，Node 22.720 ms。

| 输入 | Python 冷调用 | TS 冷调用 | Python 原版峰值 RSS | Python 配置复用峰值 RSS | TS 峰值 RSS |
|---|---:|---:|---:|---:|---:|
| 合成408篇 | 67.334 ms | 110.044 ms | 22.41 MiB | 21.66 MiB | 95.30 MiB |
| 合成10000篇 | 563.167 ms | 317.350 ms | 70.16 MiB | 52.03 MiB | 260.70 MiB |
| 真实20篇 | 41.534 ms | 110.111 ms | 20.72 MiB | 20.72 MiB | 84.98 MiB |

短脚本场景下，原生TS加载和启动开销可能超过计算收益；本地基准中TS峰值内存也更高。因此“零运行时第三方依赖”不等于“更低内存”或“更快冷启动”。未来将多个阶段放在同一进程、避免重复恢复状态，需另行对照验证。

## 正确性与交付边界

- 7项Node测试通过；其中一项批量核对15组Python参考输入，含2500篇评分压力样本、408篇排序，以及Unicode边界、特殊大小写、换行、数字、时区、微秒、舍入、门槛、同分及多样性场景。
- 所有三组基准输入（含20篇真实样本）完整输出一致；TS类型检查、原133项Python回归测试通过。
- TS保留原始排序对发布时间字符串与时间戳的不同使用方式、Unicode码点顺序和稳定排序，不在迁移中顺便改变业务规则。
- `choose`有意不修改输入，返回新文章对象；Python会修改输入。TS JSON入口要求带时区的规范ISO日期和有效配置，非法输入失败退出。这些接口约束不改变合格输入的结果。
